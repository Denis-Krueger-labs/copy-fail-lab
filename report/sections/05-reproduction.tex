\section{Vulnerable Reconstruction and Controlled Reproduction}

Chapter~4 established that VM~270 could not serve as the direct reproduction
target. The reference system was protected by two independent conditions: its
running kernel contained the Copy Fail correction, and its effective
module-loading policy prevented \code{algif\_aead} from being loaded.
VM~270 was therefore retained as the protected reference system, while the
reproduction phase continued on the separate experimental target, VM~271.

The vulnerable runtime on VM~271 was reconstructed using Ubuntu kernel
\code{6.8.0-116-generic}, supplied by package version
\code{6.8.0-116.116}. This version preceded the first corrected Noble kernel
identified in Chapter~4. Before proof-of-concept execution, the running kernel,
installed package versions, AF\_ALG module state, unprivileged user identity,
and the metadata and SHA-256 digest of the selected SUID target were recorded.

A preliminary reproduction was performed to investigate the observable effects
of the vulnerability. Because that experiment changed the mounted view of the
target file, the virtual machine was rebooted into the same vulnerable kernel
before the final evidence run. The reboot restored the original observable
target-file digest. The preserved reproduction sequence therefore began again
from a clean observable pre-exploitation state rather than continuing from the
preliminary investigation. Observations from the two runs are kept distinct
throughout this chapter.

During the preserved run, the proof of concept was executed by
\code{labuser}, an ordinary local account with UID~1001. In accordance with
the success criterion defined in Chapter~1, privilege escalation was considered
demonstrated when the resulting shell reported UID~0. No persistence,
credential collection, lateral movement, or unrelated post-exploitation
activity was performed.

The subsequent observations include the changed SHA-256 digest returned through
the normal mounted/VFS view of \code{/usr/bin/su}, comparison with a direct
read from the backing ext4 filesystem, and recovery after rebooting into the
same vulnerable kernel. These observations are reported separately so that the
demonstrated privilege escalation is not conflated with stronger claims about
the vulnerability's internal kernel state.

The following sections document the reconstructed runtime, the preserved
pre-exploitation state, controlled proof-of-concept execution, resulting
privilege transition, filesystem-view comparison, and reboot recovery. Together,
they provide the experimental basis for answering RQ1 before the investigation
moves to behavioural observation and detection engineering.

\subsection{Experimental Boundary and Preserved Evidence Sequence}

The work on VM~271 produced two logically separate experimental sequences. A
preliminary reproduction was first used to verify the intended path and explore
the resulting system state. That investigation included cache-drop tests and a
direct comparison between the normal mounted view of the target and data read
from the underlying ext4 filesystem. Because the preliminary run had already
changed the observable target state, its post-exploitation condition was not
reused as the starting point for the formal evidence sequence.

VM~271 was rebooted before the preserved run and returned to the same
vulnerable kernel. The active release remained
\code{6.8.0-116-generic}. After the reboot, the mounted view of
\code{/usr/bin/su} again produced its original known-good SHA-256 digest:

\begin{lstlisting}
c74311fe5636b7d7f9a56239fa8adeeab12ba86fe7d41b91afa85bf9bbdae78b  /usr/bin/su
\end{lstlisting}

This recovery established a clean \emph{observable} starting condition for the
selected target before the final execution. The term does not assert that every
byte of the guest or every item of volatile state was independently compared
with the original clone. It means that the same vulnerable kernel was running
and that the target's mounted-view metadata and digest had returned to their
documented pre-exploitation values.

The agreement between the active release and the three package records shows
that the intended historical kernel was not merely installed alongside a newer
runtime: it was the kernel actually running during the experiment. The final
pre-exploitation artifact independently recorded the same active release after
the reboot that separated the preliminary investigation from the preserved
run. This placed VM~271 on the pre-fix side of the vendor boundary identified
in Chapter~4; the later controlled execution provides the behavioural test of
whether that reconstructed runtime was exploitable under the laboratory
conditions.

The final pre-exploitation capture initially showed no loaded AF\_ALG modules.
However, a dry-run resolution of \code{modprobe algif\_aead} returned the
ordinary insertion path for both the dependency and the requested module:

\begin{lstlisting}
insmod /lib/modules/6.8.0-116-generic/kernel/crypto/af_alg.ko.zst
insmod /lib/modules/6.8.0-116-generic/kernel/crypto/algif_aead.ko.zst
\end{lstlisting}

This result is materially different from VM~270, where the same request
resolved to an \code{install /bin/false} policy override. On VM~271, the empty
initial module listing therefore represented an \emph{unloaded but loadable}
state rather than evidence that the interface had been disabled through that
normal loading path. The resolution output confirms the path that
\code{modprobe} would take; it does not, by itself, prove that every possible
module-loading policy or access-control path was absent.

The preliminary runtime confirmation subsequently recorded the modules in the
loaded state:

\begin{lstlisting}
algif_aead             12288  0
af_alg                 32768  1 algif_aead
\end{lstlisting}

Evidence item~02 in the preserved sequence separately records the same loaded
state after the clean pre-exploitation capture and before proof-of-concept
execution. These observations establish the module prerequisite used by the
experiment. They do not alone demonstrate a successful AEAD encrypt/decrypt
round trip, exploitation, or privilege escalation; those claims require the
later control and execution evidence.

One evidence boundary is important here. The preliminary runtime-confirmation
artifact also contains a target digest that had already changed through the
mounted/VFS view. It is therefore not used as evidence of the final
pre-exploitation target state. Only its narrowly scoped running-release,
package, and loaded-module observations are used in this subsection. The clean
target metadata and original digest are taken from evidence item~01 and are
examined in the following subsection.

Taken together, the running release, matching package records, normal module
load resolution, and subsequently recorded loaded state show that VM~271
satisfied the reconstructed kernel and AF\_ALG prerequisites for the controlled
reproduction. They establish the experimental runtime without pre-empting the
separate proof of privilege escalation.

The target metadata identifies \code{/usr/bin/su} as a regular file owned by

Immediately before execution, hashing that path through the normal mounted/VFS

\begin{lstlisting}
c74311fe5636b7d7f9a56239fa8adeeab12ba86fe7d41b91afa85bf9bbdae78b  /usr/bin/su

This digest is treated as the original known-good value within the experiment
because it was observed before the preserved execution, matched the value later
returned by the direct backing-filesystem read, and reappeared through the
mounted view after reboot. The term \emph{known-good} is therefore scoped to
the controlled comparison. It is not presented as an independently obtained
vendor-package digest or as proof that the complete guest matched its initial
clone byte for byte.

The recorded identity places the executing subject at UID~1001 and GID~1001,
with the displayed supplementary membership in the ordinary \code{users}
group. This establishes that the preserved commands were issued from the
\code{labuser} session rather than an already-root shell. The \code{id} output
does not, on its own, prove the absence of every other privilege mechanism,
such as file capabilities or a separate \code{sudo} authorization. The later
transition to UID~0 is therefore evaluated from the controlled proof-of-concept
sequence rather than inferred solely from this account listing.

The empty AF\_ALG module-state field records no matching loaded entry for either
the requested AEAD module or its displayed dependency at the time of this
capture. The load-resolution command described in the preceding subsection was
a dry run and did not itself alter that state. Evidence item~02 records the
subsequent loaded state, preserving the documented ordering between the clean
pre-exploitation capture, interface activation, and proof-of-concept execution.

The accompanying screenshot separately displays the running kernel, the
\code{id} result, and the original mounted-view digest from the interactive
\path{labuser@copyfail-vuln} session. It does not contain an embedded timestamp
or the complete file-metadata line; those fields are supplied by the associated
text artifact. The two representations are consequently corroborating but not
identical in scope.

Evidence item~01 therefore provides the before-state required for the later
comparison: a vulnerable running kernel, an observed non-root identity, a
root-owned SUID target with its original mounted-view digest, and AF\_ALG
modules not yet loaded for the final run. It establishes the observable
baseline without claiming that exploitation had already occurred or that the
entire VM state had been independently reset and verified.

\subsection{Controlled Proof-of-Concept Execution and Privilege Transition}

After evidence item~01 had established the observable baseline, the kernel
modules supporting the required AF\_ALG interface were activated as a separate
laboratory preparation step. Evidence item~02 records the \code{researcher}
account using administrative privilege to load \code{algif\_aead}, followed by
a module-state query whose visible output was:

\begin{lstlisting}
algif_aead             12288  0
af_alg                 32768  1 algif_aead
\end{lstlisting}

This step is not counted as the privilege escalation. It documents that a
privileged laboratory operator prepared the required module state before the
test, while the proof of concept itself was subsequently launched from the
separate \code{labuser} session. The evidence therefore does not imply that an
unprivileged account could load a restricted kernel module; module activation
and vulnerability exploitation are treated as distinct actions.

Evidence item~03 begins with the ordinary-user prompt and records the following
execution and validation sequence:

\begin{lstlisting}
labuser@copyfail-vuln:~$ python3 ~/copy_fail_exp.py
# id
uid=0(root) gid=1001(labuser) groups=1001(labuser),100(users)
# whoami
root
\end{lstlisting}

The execution command is shown without \code{sudo}, \code{su}, or another
explicit privilege-granting wrapper. After the proof-of-concept command was
launched, the visible prompt changed from the ordinary \code{\$} form to
\code{\#}. That visual change is consistent with a privileged shell, but it is
not used as the sole success indicator. The subsequent \code{id} and
\code{whoami} results directly record UID~0 and the resolved user name
\code{root}.

The primary group remained GID~1001 and the displayed group memberships
remained those of \code{labuser}. The demonstrated result is therefore a
transition to root user identity rather than a claim that every element of the
process credentials was replaced with the conventional root-group state. UID~0
nonetheless satisfies the privilege-escalation success criterion defined in
Chapter~1 and is sufficient to answer the reproduction component of RQ1.

The complete proof-of-concept source is not redistributed. The local
731-byte representation associated with the reproduction was instead
identified by the following SHA-256 digest:

\begin{lstlisting}
d401e7d1c00605749d6c617ace73ab20a762b72e41c2e1590331596e38219a61
\end{lstlisting}

The absent evidence position~04 originally contained a screenshot of the
complete source and was intentionally removed from the public package. A
separately recorded 732-byte representation differed by one trailing newline
and was not executed. The hash above therefore identifies the documented local
731-byte representation; it is not substituted with the later newline variant.
This preserves byte-level identity for the retained sample without publishing
the exploit source in the report. Because evidence item~03 does not display a
hash calculated immediately before launch, the recorded digest provides source
provenance rather than a cryptographic binding between the screenshot and the
exact bytes present at that moment.

The execution screenshot also records that the SHA-256 digest obtained from
the mounted path \code{/usr/bin/su} had changed to:

\begin{lstlisting}
44900c631391f0d60eb6d271b8374a08dc1d9be76e403390d27a91ed5f179be9
\end{lstlisting}

That adjacent observation is not required to prove the UID transition and is
not interpreted here as evidence of a persistent on-disk replacement. The
post-exploitation mounted view, the direct backing-filesystem comparison, and
the reboot result are examined separately in the following subsections.

Evidence items~02 and~03 are screenshot-only records and do not contain an
embedded wall-clock timestamp. Their content supports the displayed module
state, execution command, and identity results, while their ordering is derived
from the preserved evidence sequence and its accompanying documentation rather
than independently reconstructed from screenshot timestamps. No persistence,
credential access, lateral movement, or unrelated post-exploitation action is
claimed from this sequence.

Within these limits, the result is direct: a command launched from the recorded
UID~1001 \code{labuser} context on the reconstructed vulnerable runtime
produced a shell whose identity checks returned UID~0 and \code{root}. The
controlled reproduction therefore demonstrated the intended local privilege
escalation without relying on the changed target digest as a proxy for success.

\subsection{Post-Exploitation Mounted-View State}

Evidence item~05 was captured at \code{2026-08-08 23:24:57 UTC}, after the
privileged shell shown in evidence item~03 had been exited. The text artifact
and accompanying screenshot record the following state:

\begin{lstlisting}
6.8.0-116-generic
uid=1001(labuser) gid=1001(labuser) groups=1001(labuser),100(users)
labuser
-rwsr-xr-x root root 55680 /usr/bin/su
44900c631391f0d60eb6d271b8374a08dc1d9be76e403390d27a91ed5f179be9  /usr/bin/su
\end{lstlisting}

The identity output shows that the interactive session had returned to
UID~1001 and that \code{whoami} again resolved to \code{labuser}. The target
remained owned by \code{root:root}, retained its set-user-ID mode, and remained
55,680~bytes in size. These metadata values match the pre-exploitation capture.
The observable difference was the byte stream returned through the normal
mounted path, whose SHA-256 digest remained the changed value first shown in
evidence item~03.

Leaving the UID~0 shell therefore did not immediately restore the original
mounted view of \code{/usr/bin/su}. This continued observation is distinct from
post-exploitation persistence in the usual security sense: no mechanism was
installed to survive reboot, retain privileged access, or automatically
re-establish the altered state. It records only that the changed mounted-view
content remained visible after the privileged shell had ended and while the
system continued running.

The unchanged size, ownership, and permission bits also show why metadata-only
monitoring would not have captured the observed content change in this run.
Conversely, the changed digest proves only that the bytes returned through that
path differed from the baseline. A cryptographic hash does not reveal the
number, positions, or meaning of the differing bytes, and it does not by itself
identify whether the persistent-storage representation changed.

This post-exploitation capture consequently establishes an intermediate state:
the test user was again non-root, the privileged target retained its original
filesystem metadata, and the altered mounted-view digest remained observable.
The next comparison tests whether the same changed bytes were also returned
when the target was read through a separate backing-filesystem path.

\subsection{Mounted-View and Backing-Filesystem Comparison}

Evidence item~06 was captured at \code{2026-08-08 23:28:41 UTC}. The same
\code{6.8.0-116-generic} kernel remained active. The normal mounted path was
hashed again and compared with a read performed directly against the ext4
filesystem on the underlying logical volume. The evidence documentation records
the diagnostic command as:

\begin{lstlisting}
sudo debugfs -R 'cat /usr/bin/su' \
  /dev/mapper/ubuntu--vg-ubuntu--lv 2>/dev/null \
  | sha256sum
\end{lstlisting}

This administrative diagnostic was performed after the UID~0 result and did
not contribute to the privilege transition. Its purpose was to compare two
ways of reading the same logical target. The preserved results were:

\begin{lstlisting}
Mounted/VFS view:
44900c631391f0d60eb6d271b8374a08dc1d9be76e403390d27a91ed5f179be9  /usr/bin/su

ext4 backing filesystem view:
c74311fe5636b7d7f9a56239fa8adeeab12ba86fe7d41b91afa85bf9bbdae78b  -
\end{lstlisting}

The mounted/VFS access path continued to return the changed digest, whereas the
\code{debugfs} read returned the original digest recorded before exploitation.
The two access paths therefore produced different byte streams at the time of
the comparison. This is consistent with the published Copy Fail mechanism, in
which a file's cached representation can be modified without the corresponding
change being written back to the persistent filesystem
\cite{copyfail-research}.

The experiment nevertheless distinguishes that interpretation from what the
artifact proves directly. No kernel instrumentation captured the relevant page
objects, dirty-state flags, scatterlists, or writeback decisions during this
comparison. The evidence therefore establishes an access-path divergence; it
does not independently identify the page cache as the causal storage location
or reconstruct the internal kernel state responsible for the different reads.

The \code{debugfs} result is also a point-in-time read from a live laboratory
filesystem rather than a complete forensic disk image or an offline filesystem
verification. No concurrent modification of the target was intentionally
performed during the comparison, but the result should not be expanded into a
claim about every block, cache layer, or filesystem object in the guest.

Within those limits, evidence item~06 supports the narrower and experimentally
important conclusion: the altered content was observable through the mounted
path while the separate ext4 read still returned the original target content.
This explains why the changed mounted-view digest alone was not classified as
proof of a persistent on-disk replacement.

\subsection{Recovery After Reboot into the Same Vulnerable Kernel}

The final preserved phase tested whether the altered mounted view remained
after a reboot. The first recovery screenshot was captured at
\code{2026-08-08 23:30:53 UTC} and records the active release and target digest
as:

\begin{lstlisting}
6.8.0-116-generic
c74311fe5636b7d7f9a56239fa8adeeab12ba86fe7d41b91afa85bf9bbdae78b  /usr/bin/su
\end{lstlisting}

A separate machine-readable recovery artifact was captured later, at
\code{2026-08-08 23:36:42 UTC}. It again records
\code{6.8.0-116-generic}, identifies the active session as the
\code{researcher} account, and preserves the target state as:

\begin{lstlisting}
-rwsr-xr-x root root 55680 /usr/bin/su
c74311fe5636b7d7f9a56239fa8adeeab12ba86fe7d41b91afa85bf9bbdae78b  /usr/bin/su
\end{lstlisting}

The screenshot and text artifact are therefore two post-reboot observations,
not duplicate representations of one simultaneous command. Both show that the
normal mounted path had returned to the original digest, while the later text
capture additionally confirms the original size, ownership, and set-user-ID
mode. The account used for the recovery check differs from the exploitation
subject, but that identity difference does not alter the target-path digest
being compared.

Because the running release remained \code{6.8.0-116-generic}, restoration did
not depend on installing or booting a corrected kernel. Under the tested
conditions, rebooting into the same vulnerable release removed the previously
observable mounted-view divergence. This result is consistent with a transient
in-memory modification and with the original bytes remaining available from
the backing filesystem during evidence item~06.

Recovery of the target view is not equivalent to remediation. The same
vulnerable kernel and loadable module path remained present after reboot, so the
laboratory conditions required for another reproduction could be restored. A
reboot can clear the observed transient state, but it does not correct the
kernel flaw or provide a durable security boundary.

The preserved recovery records do not include a boot identifier, an uptime
comparison, or a reboot-journal excerpt. The reboot event is therefore supplied
by the documented experimental sequence rather than independently proven by
those two captures alone. The captures directly establish only the state shown
after the declared reboot: the same vulnerable kernel was active and the
mounted target once again produced its original digest.

\subsection{Reproduction Result and Answer to RQ1}

The controlled sequence provides a coherent before, execution, and recovery
record. VM~271 began the preserved run on the reconstructed
\code{6.8.0-116-generic} runtime with \code{labuser} at UID~1001 and a
root-owned SUID target whose mounted-view digest matched the original value.
After the required modules were loaded by the separate \code{researcher}
account, the proof of concept was launched from the \code{labuser} prompt
without an explicit privilege-granting wrapper. The resulting shell returned
UID~0 and \code{root}.

The post-exploitation captures then showed that the session could return to
UID~1001 while the changed target digest remained observable through the
mounted path. A separate ext4 read returned the original digest, and a reboot
into the same vulnerable kernel restored the original mounted-view digest. The
principal findings and their evidential limits are summarised in
\cref{tab:reproduction-findings}.

RQ1 asks whether Copy Fail can be reproduced reliably in the isolated
laboratory by an ordinary, unprivileged local user. For the tested configuration,
the result supports an affirmative answer: the preserved run begins with the
dedicated test account at UID~1001 and records the proof-of-concept execution
producing a UID~0 shell. The preliminary investigation and the restarted final
run both produced the expected changed mounted view, while the final run
preserved the direct UID~0 validation.

The word \emph{reliably} remains bounded by the experimental design. The public
evidence does not contain a multi-host trial matrix, a success/failure count, or
a statistical timing analysis. It demonstrates operational repeatability on
the same reconstructed VM and a directly validated privilege transition in the
preserved run; it does not quantify an exploit success rate across other
kernels, hardware, workloads, or timing conditions.

The UID~0 result, rather than the changed file digest, is the decisive answer to
RQ1. The digest sequence provides supporting behavioural context and shows that
the mounted-view alteration was transient under the tested recovery procedure.
With reproduction established, the following chapter examines which parts of
this sequence are consistently observable and which can serve as behavioural
detection opportunities without depending on the specific proof-of-concept
filename or hash.
